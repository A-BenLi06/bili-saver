## E1 时间戳必须机器生成，禁止手估

- **原理**：异步协作的所有时序判断——冲突裁决"以留言时间戳为准"、claim 超时接管、昼夜窗口切换——都压在时间戳上。LLM agent 对"现在几点"会估计而不是查表，且多会话可能跑在不同 TZ 的环境里，漂移是系统性的不是偶发的。
- **做法**：协议明文规定 `date '+%Y-%m-%d %H:%M'`（本地）/ `date -u`（UTC）实测；发现自己旧条目时间错→**追加更正条、不改原文**（保留审计链）；多环境协作（WSL/容器/远程）开工前各跑一遍 `date` 核对一致。
- **证据**：P-001——ui-agent 与 session-agent 同夜时间戳一致性地快 1h（"02:45"的交接写于 mtime 01:45 的文件），判共同来源（环境 TZ）而非个体失误。
- **迁移**：任何项目 Day 0 就写进协议第一条。本项目教训：等发现时已经两天的条目不可信。

## E2 文档里的全局事实会腐化，需巡检核对

- **原理**：包数、schema 版本、端口号、默认值这类"全局事实"散落在多处文档，改动者只更新自己眼前的那处；文档没有测试，腐化无门禁报错。
- **做法**：① 改动触碰全局事实的人，顺手全文 grep 旧值；② 巡检 agent 定期做"文档自洽性核对"（如同文件 §3 说 v5、§5 迁移历史说 v8 的自相矛盾，一眼可断）；③ 全局事实尽量**单点定义**（一处写死，别处引用）。
- **证据**：P-002——ARCHITECTURE 同文件内 §3"schema v5" vs §5 迁移历史 v8 自相矛盾；AGENTS"11 包"落后实际 20 包近三天，期间 6+ 项交付都按 20 包验收没人发现文档错。
- **迁移**：巡检清单固定项。有 CI 的项目可写个文档数字的 lint（如 grep 包数断言）。

## E3 共享文件并发编辑：精确锚点+断言即停+工具护栏

- **原理**：多个 agent 并行写同一文件时，"读-改-写"窗口内的他人写入必然发生；**无 git 的仓库里文件是唯一共享状态**，覆盖即丢失。
- **做法**：① 改前重读目标块（禁止凭记忆/早前读取做替换）；② 脚本化修改先 grep 验锚点，断言失败即停检查并行改动，**永不放宽匹配**；③ 用带 staleness 检测的编辑工具作护栏（工具层"文件已被修改"报错强制的重读，比自觉可靠）；④ 结构性改动（共享 struct/路由表）必须 @all 广播。
- **证据**：COORDINATION §3 记载三次锚点漂移事故；coord-agent 2026-09-09 首轮 30 分钟内亲历 2 次（ARCHITECTURE.md 编辑时被并行写入、CLAIMS.md 两次），全部被"改前重读+工具 staleness 报错"拦截，零丢失。
- **迁移**：有 git 的项目降级为分支+PR 纪律（冲突由 merge 暴露）；无 git 项目本条是红线级。**下一个项目尽量上 git**，本条一半的成本就消失了。
- **[补充 2026-09-09 02:2x] 本项目已引入 git**（walkthrough-agent 兼任独家管理，基线提交 7a94910，定时快照提交，其他 agent 不碰 git）：锚点纪律**仍然全程适用**——快照是小时级的，git 解决的是"丢改动可回溯"，不解决"实时写丢"；并发编辑防护依旧靠改前重读+锚点断言+工具 staleness 拦截。两类机制互补，勿因有 git 而松懈前者。

## E4 "门绿"是时点快照；并行半成品阻塞时按包验证

- **原理**：全量验收门（build+vet+test）是共享资源，任一 agent 的 WIP 都会弄红它；他人引用"门绿"结论时若不重跑，等于把自己的验证建立在别人的过去时状态上。
- **做法**：① 门红先查 CLAIMS 判归属（哪家的 active/wip claim），**归属明确的红=正常开发中态，不是事故**；② 自己的改动用按包验证自证（涉及包单独 build/vet/test 全绿），全量复绿后才置 done；③ 永不代改他人测试/代码"修门"；④ 巡检每轮跑门禁并判归属，新红灯预警、旧红灯复绿关单。
- **证据**：P-008——ui-agent 交接（~01:3x）称门全绿，02:00 即红（session-agent TestPatchConfig panic）；ui-agent 当夜两度被 teriteri 半成品阻塞、按包验证零冲突通过，证明该模式可行。
- **[补充 2026-09-09 02:53] "红"不只在门禁，也在运行时**：巡检只看 build/test 会漏掉运行时的慢性红——如 P-009 的失败循环（150/152 条失败全是同一根因，被每分钟重试放大）在门禁全绿下持续刷库。巡检清单必须含**运行时失败率/错误集中度**检查：失败集中在单一根因=一条系统性红牌（判 owner、留言、勿代改）；偶发分散失败=背景噪声。"失败率的突增或高度集中"与"门红"同级别对待。
- **迁移**：任何共享 CI/构建环境同理。有 git 项目对应"main 红了先看是谁的 PR 在跑"。

## E5 派生索引/缓存：验收必须含"存量回填+增量接线"双证据

- **原理**：给存量数据加索引/缓存/派生层时，最容易只交付"机制"（函数、表）而不交付"喂食"（谁来回填存量、谁在增量路径上调用）。端点 200 ≠ 机制在工作。
- **做法**：验收清单固定两问：存量数据谁回填、回填了多少（数字）？增量路径接在哪一行、失败是否阻断主链路？两个都有答案才 done。
- **证据**：P-006——comments_fts 建表即有、重建函数即有，但全仓零调用、存量 0 行，搜索端点空转至被发现为止（3.2 万条一次性回填+UpsertComment 尾部增量才救活）。
- **迁移**：凡是"派生于原数据"的东西（缓存、索引、物化视图、导出文件）通用。

## E6 半成品不代改：所有权 > 效率

- **原理**：代改他人半成品看似省时间，实际三重代价：抢先提交的方案未必符合作者意图（返工双份）、所有权边界被打破后所有人开始互相改（混沌）、作者失去对自己区域的上下文连续性。留言催促+按包绕行的等待成本远低于此。
- **做法**：发现他人区域编译坏/半成品：a) 自己绕行（按包验证）；b) 留言催促写明阻塞点；c) 仅当 owner 失联超时（协议 §2 时限）才最小化恢复——回退到可编译等价态，不做功能级替写。
- **证据**：本项目 card 半成品阻塞全量门期间，core/ui 均留言+绕行，无一代改；card 新会话接管后自行修复，交接顺畅。反例见 COORDINATION §3.4（用户明令禁止代改的由来）。
- **迁移**：通用。多 agent 互不代改是多智能体软件工程里少有的"零争议"规则。

## E7 agent 上下文范围管理：开场最小阅读集

- **原理**：每个新会话的上下文预算有限且贵。读少了会撞并行改动与红线；读多了重点被淹没、行为变差。上下文管理本质是**给每类会话定义"必读/按需/不读"三层**，并把状态压缩成高密度摘要供快速恢复。
- **做法**（本项目验证有效的分层）：
  1. **必读三件**（开工前，顺序固定）：AGENTS.md（红线+环境+检查清单）→ CLAIMS.md（只看：留言区 @自己/@all 的未处理消息 + 登记表中目标文件相关行）→ **目标代码块**（不是整文件，grep 定位后读局部）。
  2. **按需读**：ARCHITECTURE 相关节（改到哪读到哪）、PITFALLS 索引表（写码前扫一眼，全文检索按需）、WALKTHROUGH 尾部（想知道"最近发生了什么"时）。
  3. **明确不读**：与自己区域无关的 claim 行详情、raw 流水全文、历史已处理留言。
  4. **状态压缩靠登记行**：claim 行=一项工作的完整上下文（区域/owner/状态/方案/验证证据），会话失效后新会话**先读行再读码**即可接管，不从零考古。
  5. **交接摘要四段式**：完成了什么 / 验证方式与证据 / 建议抽查项 / 挂起项。人类晨间 5 分钟可评审一晚的产出。
- **证据**：card-agent 会话失效后新会话凭登记行+交接完成接管收尾（CLAIMS 9月8日 16:45 条）；本项目一晚 6+ 项交付的晨报全部四段式，评审负担未见增长。
- **迁移**：三件套的**文件名**可换，分层结构别省。特别注意：把"读留言"放进必读层——漏读留言是并行冲突的最大来源。

## E8 职能配置：角色按"区域×时效"划分

- **原理**：多 agent 项目的混乱常源于角色模糊而非能力不足。有效维度是两个：**独占区域**（谁的领地）和**时效**（长期在岗还是一次性任务）。
- **做法**（本项目实际配置，已验证）：
  - **长期维护型**（core-agent）：守护存量代码与公共链路，别人动他的文件要留言打招呼。
  - **任务型**（ui/session/perf/card…）：人类交办一单做一单，done 后文件回归共享池；同一 feature 只有一个 owner。
  - **后台自动化型**（walkthrough-agent 每小时、coord-agent 每 15min）：定时 cron 驱动，只写自己的文件，不参与功能开发。
  - **评审者**（人类）：白天在线裁决，夜间授权自主执行+晨报追认——昼夜分级 L1 直接做/L2 做完待抽查/L3 仅红线·方向·发布挂起。
  - **协调者**（coord-agent）：不写功能代码，负责巡检（留言/门禁/服务健康）、坑台账、经验库、协议演进建议。
- **反模式与化解**：两个任务型 agent 同期要改同一共享文件——本项目用"**声明互不重叠作业区**"化解（session 改设置页、ui 改跟踪列表，同在 index.html/admin.go，各自在 claim 行写明只动哪个函数/区块，零冲突通过）。
- **迁移**：最小配置=1 长期维护 + N 任务 + 1 巡检；任务量大再加记录型。角色表写进 AGENTS.md，开工前人人可见。

## E9 交流协议：文件留言板的三要素与状态机

- **原理**：无即时通讯的异步协作里，留言板是唯一通道；消息丢/没人认领/不知是否已读，都会让协作退化为各干各的。
- **做法**：① 每条留言三要素齐全：改了什么（变更通知）/ 需要对方做什么（行动项）/ 约定（后续规则）；② @ 精确到 owner，广播（@all）有门槛——结构性改动、系统性坑、协议生效才用；③ 状态原地标记（待处理→已处理 ✓/已解决），**处理后标自己的留言**，读到的 @all 广播由发起人按回执统一关；④ 留言板与登记表放同一文件——读登记必路过留言，天然防漏读；⑤ 30 天归档制。
- **证据**：CLAIMS.md 运行两日 20+ 条留言，每条有归属有状态，零丢失；ui→core 的 FTS 写路径通知发出后 core 收到即知晓，避免不知情冲突。
- **迁移**：直接搬。唯一要按项目定的是广播门槛细则。

## E10 验证阶梯替代"人工确认"（无人值守的完成标准）

- **原理**：夜间/无人值守窗口里，"需要人工测试确认"若可作为挂起理由，窗口就空转；但要防止用"自测过了"敷衍，所以需要一个**客观的逐级证据阶梯**。
- **做法**：四级阶梯——单测/mock → 起服务+脚本断言（状态码+关键字段）→ 真实外部接口只读冒烟（限流内）→ 浏览器自动化截图留证。逐级尝试，通过即算确认完成，证据写进晨报。配分级：L1 直接 done / L2 done-review（共享热点结构改动、API 形状变化、schema 迁移——做完不阻塞他人，晨间提示抽查）/ L3 挂起（仅红线语义、数据删除、产品方向、外部发布）。
- **证据**：协议生效首夜 6+ 项交付全部带四级证据，零"等人工"挂起；两项 L2（API 形状变化、调度语义变化）按机制留待晨间抽查，依赖它们的 agent 未被阻塞。
- **迁移**：阶梯内容按技术栈替换（Web=Playwright 截图；CLI=golden file；数据管道=对账脚本），骨架（逐级+留证+分级）不动。

3. **配两个后台角色**：巡检 agent（cron：活跃窗口高频/人在线时停——理由 E2/E4；巡检项：留言处理、门禁健康判归属、服务健康、坑入库、经验提炼）+ 记录 agent（walkthrough，流水只增不改）。
4. **时区对齐**（E1）：所有参与环境跑 `date` 核对一致后才开工。
5. **版本控制**（E3）：能上 git 就上 git；上不了则 E3 全量条款当红线。
6. **定义昼夜分级与验证阶梯**（E10）：按项目技术栈填四级阶梯内容；明确 L2 清单（什么算"需抽查"）。
7. **第一个 @all**：宣布协议生效+当前 claim 登记 + 老工作的补登记规则（本项目 core-agent 首夜做法，运转良好）。

## 协调者的运用方式（经验如何反哺日常协调）

- 巡检每轮执行：E1（核查新留言时间戳合理性）、E4（门禁+归属判定）、E2（文档数字抽查，低频）、E6（发现代改冲动时拦截自己）。
- 协调决策引用经验编号（如"按 E4 判定归属，不预警为事故"），保证裁决一致性、可追溯。
- 坑（PITFALLS）与经验（本文件）的转化时机：新坑入库时问一句"这是本项目特有还是模式？"——模式类的同轮提炼进本文件；不确定的先躺台账，重复出现第二次再提炼。
