# 本地爬山测试与改进

把最近一次通过验证的提交当作当前基线。每轮只试一个可回退的补丁，并在测量前写明主要指标、保护指标和通过线。候选先按影响、把握、成本排序。正确性和归档数据完整性是硬门槛，性能换不来例外。

| 首批顺序 | 候选 | 影响 | 把握 | 成本 |
| --- | --- | --- | --- | --- |
| 1 | 按日志序号定位新增行，减少空轮询扫描 | 高频日志轮询 | 高 | 低 |
| 2 | 按需一次性复制快照，减少历史分页的分配 | 首屏及堆积日志读取 | 高 | 低 |
| 3 | 缓冲小块归档输出的比较读取 | 可能减少文件读取调用 | 中 | 中，需大块写入和缩短输出的对照 |

1. 从最近一次通过的本地提交创建干净的临时 worktree。在实验分支只改一个行为。两侧保留同一基准用例和输入，且测量时不要编辑。正确性修复用可复现的失败用例作为主要证据，先证实旧实现失败，再验证新实现和所有保护项。下面的脚本用于具备 Go 微基准的性能候选。
2. 对基线和候选运行相关包测试、构建、vet、完整内部测试和 diff 检查，再对候选跑相关包的 race 检测。脚本在单 CPU 配置下串行测量，交替先跑基线和候选。默认 5 对，每个场景每次 200 ms。
3. 主要场景的延迟中位数须至少降低 10%，且过半配对各自达到该门槛。其他场景延迟中位数最多上升 15%。所有场景的每次分配字节数、次数中位数都不得上升。结果只代表指定合成负载，不等于线上端到端延迟。
4. 比较原始日志、检查 diff，确认通过后仅在本地提交，该提交成为下一轮基线。拒绝时先保存候选 diff，再在独立实验分支只恢复本轮文件。基线失败、缺少样本或环境异常时结论为 inconclusive，排除原因后才重测。不要为了通过调整门槛，也不要不断重复直到出现有利结果。
5. 每轮从剩余候选中重新排序。默认一批最多 2 个候选。连续 2 个拒绝、没有可信候选或基线不再可靠时停止，记录证据并重新选目标。这是有界的本地流程，由维护者提供补丁并复核，脚本负责量化判定。

从实验分支根目录运行。将 `/tmp/bili-base` 换成独立的临时路径，确保当前 Go 工具链与 `go.mod` 一致。输出目录必须是新目录，建议放在实验工作区外，便于保存和对照。

```bash
git worktree add --detach /tmp/bili-base <最近通过的SHA>
python3 scripts/hill_climb.py \
  --base /tmp/bili-base --candidate . --out /tmp/bili-round-01 \
  --package ./internal/logging \
  --cases RingSnapshot/CaughtUp RingSnapshot/Recent RingSnapshot/Backlog \
  --primary RingSnapshot/CaughtUp
```

日志场景使用 4,000 条合成记录。CaughtUp 表示没有新日志，Recent 表示读取 8 行，Backlog 表示读取首页上限 1,000 行。测试使用临时数据和本地 mock。退出码 0 表示通过，1 表示拒绝，2 表示没有可靠结论。输出包含 `decision.json`、每次基准输出及各门槛日志。

## 首批结果

Linux amd64，Go 1.27.1。每轮使用 5 对采样。下表记录主要场景及当轮保护指标，延迟为中位数。

| 轮次 | 基线 | 保留提交 | 主要场景 | 保护指标 |
| --- | --- | --- | --- | --- |
| 1 按序号定位 | `236452b` | `92a0fcf` | CaughtUp 3,652 → 13.10 ns/op（−99.6%） | Recent −93.0%，Backlog −6.1%，分配无增加 |
| 2 一次性复制 | `92a0fcf` | `fe9acd9` | Backlog 23,705 → 7,754 ns/op（−67.3%），11 → 1 次分配，89,760 → 40,960 B/op | Recent −59.8%，CaughtUp 13.21 → 14.45 ns/op（+9.4%，低于 15% 上限），分配无增加 |

两轮候选的针对性测试、全量内部测试、构建、vet、日志包 race 检测和 diff 检查均通过。新增回归测试覆盖缓冲淘汰后的序号、分页边界和副本隔离。

第一次采集因基准筛选漏掉 `Benchmark` 前缀而无结论。修复筛选后用原门槛重新采样。独立 Cloud 工作区保留了三次运行的日志、决策 JSON 和候选补丁，目录为 `/workspace/bili-hill-results/`。

## 第二批：250 轮归档写入实验

从首批结果继续，选择归档文件的流式比较。用 25 个读缓冲大小（8–32 KiB）与 10 个预读阈值（256 字节–8 KiB）组成 250 个不同候选。每轮优先试距离当前配置最近的未测试组合。每个候选先验证文件字节、修改时间、截短替换、失败时原件保留和临时文件清理，再交替测量 5 对。测量覆盖混合块大小、64 KiB 块和短文件。筛选沿用 10% 主指标改善和 15% 保护上限，只用于选配置。

250 轮均完成，247 轮未提升筛选基线，第 1、56、189 轮更新了筛选基线。最后以第 189 轮（15 KiB 缓冲、写入块小于 1 KiB 时预读）对照原实现 `959ac82`，在独立工作树按原门槛重新测量。独立复核另测了需要实际替换文件的场景和每次分配量。最终保留提交为 `be9ecfe`。

| 独立复核场景 | 基线中位数 | 候选中位数 | 变化 |
| --- | ---: | ---: | ---: |
| 混合块大小，内容不变 | 81.86 µs | 66.50 µs | −18.8% |
| 64 KiB 块，内容不变 | 64.45 µs | 62.55 µs | −3.0% |
| 4 KiB 文件，内容不变 | 7.86 µs | 5.00 µs | −36.4% |
| 替换文件 | 1,185.36 µs | 1,040.60 µs | −12.2% |

混合场景有 4/5 对达到 10% 改善门槛，每次分配字节数由 41,128 降至 16,552，分配次数仍为 4。替换场景包含同步到盘，单次耗时波动较大。数据是在 Linux Cloud 上用合成文件测量，适合比较此文件路径，不能推断下载或整个归档的收益。

Cloud 工作区 `/workspace/bili-hill-250-results/` 保留逐轮 JSONL、复跑说明、筛选实现补丁与测试源码、独立复核和测试日志。短测筛选和完整验收分别记录，250 轮中只有最终领先配置进入独立复核。

## 日志数据结构与源码整理

将内存日志从按尾部追加、截断切片改成固定 4,000 个槽位的环，并移入 `internal/logging/ring.go`。顺序编号可直接定位槽位，跨环边界的快照按原顺序复制。第一版虽减少了分配，只有 2/5 对写入测量达到延迟门槛，因此回退。第二版同时避免创建拆行临时切片，按同一基线和门槛完成复核。

| 场景 | 基线中位数 | 保留版中位数 |
| --- | ---: | ---: |
| 满载时追加一行 | 242.6 ns | 206.7 ns（−14.8%） |
| 没有新增日志 | 16.15 ns | 6.52 ns（−59.6%） |
| 跨环边界读取 1,000 行 | 10.65 µs | 9.15 µs（−14.1%） |

满载写入由 272 B/op 降至 96 B/op，分配次数由 3 降至 2。代价是首次接收有效日志时分配整组槽位。构建、vet、全部内部测试和日志包 race 通过，另验证跨环读取及快照不可修改内部数据。原始记录保存在 Cloud 工作区 `/workspace/bili-structures-results/`。

## 深查归档数据操作

这批分别测量原件 ZIP 导出、共享资产校验、原始 gzip 快照校验。每项按五对样本与当前基线比较，使用临时 SQLite 库和合成文件。分配量是 Go 基准测得的累计分配字节/次。

| 路径与测试量 | 耗时中位数 | 分配量中位数 | 保留提交 |
| --- | ---: | ---: | --- |
| 原件 ZIP 导出，24,000 条评论和弹幕 | 229.18 → 179.76 ms | 66.48 → 16.95 MB | `ac2b85e` |
| 离线校验，120 条资产记录共用 12 个文件 | 26.02 → 4.50 ms | 32.02 → 3.23 MB | `213f8ed` |
| 资产校验对照，120 个不同文件 | 27.94 → 27.16 ms | 32.02 → 31.92 MB | `213f8ed` |
| 离线校验，256 个 gzip 快照 | 11.25 → 8.28 ms | 20.93 → 1.00 MB | `afb5be5` |

导出在单个 ZIP 条目内复用 SQLite 扫描参数和 JSON 映射，保持读事务、字段、排序及原件过滤。新增检查覆盖 Unicode、SQLite 字节字段、64 位整数 ID 和已消失记录。共享资产在一次持有归档锁的离线检查内按相同存储键分组，仅计算一次文件摘要，各条记录独立校验大小与哈希并按原顺序报告。快照复用解压器和读取缓冲，仍读到 EOF 比对 gzip 校验信息并验证 SHA-256。回归覆盖坏头、坏校验和与取消后仍能检查下一个文件。所有候选均通过构建、vet、全量内部测试和相关包竞态检查。

原始对照和门槛日志位于 Cloud 工作区 `/workspace/bili-data-results/`。

## 备份与可移植资产目录

备份复制源文件时计算大小和 SHA-256，并在同一次操作内复用复制缓冲。数据库快照和生成的启动配置仍在生成后计算摘要。发布前仍独立复读暂存文件，并验证摘要、大小和 SQLite 完整性。恢复路径复用复制缓冲，保留复制前后两道校验。

| 合成负载 | 耗时中位数 | 每次累计分配量 |
| --- | ---: | ---: |
| 备份 4 个 8 MiB 媒体文件 | 89.13 → 75.91 ms（−14.8%） | 3.74 → 1.90 MB |
| 备份 96 个 32 KiB 文件 | 78.13 → 69.89 ms（−10.5%） | 76.78 → 26.69 MB |

测试验证了清单对应源内容，并经过备份恢复、损坏备份拒绝、完整构建、vet、全量内部测试及 archiveops 竞态检查。

资产目录用窄查询直接构建清单。20,000 条资产导出耗时从 53.13 ms 降至 30.53 ms（−42.5%），累计分配从 45.74 MB 降至 17.82 MB（−61.0%）。回归验证目录字段、原顺序及空目录。对照数据位于 Cloud 工作区 `/workspace/bili-backup-results/`。

## 文件校验缓冲复用

备份和恢复在每次清单校验中使用一个顺序摘要器。离线资产检查在本次检查内复用另一个摘要器。两项都继续完整读取实际文件并验证每条记录的摘要和大小。首要指标为每次累计分配字节数，预先要求五对测量均改善至少 30%，各场景分配次数与字节数的中位数不得增长，耗时中位数不得回退超过 15%。

| 场景 | 耗时中位数 | 每次累计分配 |
| --- | ---: | ---: |
| 备份 96 个小文件 | 61.79 → 56.97 ms | 26.69 → 1.47 MB（−94.5%） |
| 校验 120 个独立资产文件 | 27.55 → 24.73 ms | 31.92 → 0.73 MB（−97.7%） |

备份通过内存门槛，未达到原先的延迟改善门槛。资产检查同时通过内存和延迟门槛。后者首次验收在未修改的基线遇到插件槽位测试偶发失败，重跑的全量测试通过后才进行性能比较。证据和判定脚本保存在 `/workspace/bili-verify-results/`。

## 恢复与迁移的路径重写

在同一 SQLite 事务内校验每条视频和字幕路径，只为规范化后发生变化的值执行更新。第一轮只跳过无效更新，全旧格式场景的累计分配增加 3.8%，因此回退。第二轮同时复用扫描变量和每张表的更新语句文本，沿用原门槛，主场景 5/5 对均改善超过 10%。基线为 `1a320b5`，保留提交为 `23003c3`。

每次测量处理 4,000 条视频和 4,000 条字幕路径，混合场景中 10% 是历史 Windows 路径。耗时为恢复与迁移共用的数据库路径重写及配置生成步骤，不含归档文件复制。下表为 Linux amd64 上五对测量的中位数。

| 路径格式 | 耗时 | 每次累计分配量 |
| --- | ---: | ---: |
| 已是可移植格式 | 74.00 → 10.40 ms（−85.9%） | 6.92 → 1.45 MB |
| 混合 | 81.96 → 17.71 ms（−78.4%） | 6.34 → 1.88 MB |
| 全为历史格式 | 82.20 → 78.92 ms（−4.0%） | 7.19 → 6.88 MB |

新增端到端迁移回归通过 SQLite 测试触发器识别无效写入，并核对旧视频及字幕路径的转换。基线按预期触发失败，保留版通过。构建、vet、全量内部测试和 archiveops 竞态检查均通过。原始样本、判定和第一轮回退补丁位于 `/workspace/bili-relocation-results/`。

## 弹幕分段解码

从 `ead4095` 出发，用四种合成 protobuf 输入比较六个候选。每轮交替测五对，主要指标是 1,500 条弹幕的解码耗时。中位数和至少三对的改善须达到 10%。保护场景的中位耗时回退上限为 15%，所有场景的中位分配量及次数不得增加。

| 轮次 | 密集分段耗时中位数 | 判定 |
| --- | ---: | --- |
| 1 抽出单字节变长整数分支 | 169.78 → 187.43 µs | 回退，密集和仅未知字段均变慢 |
| 2 先按 wire type 再按字段号分派 | 162.83 → 161.46 µs | 回退，主要指标改善不足 |
| 3 按剩余元素数预留结果切片 | 169.13 → 179.08 µs | 回退，分配少 45%，额外扫描使解码变慢 |
| 4 直接读取单字节字段键 | 164.02 → 151.02 µs | 回退，只有两对达到 10% |
| 5 在变长整数循环前截取有效字节 | 164.47 → 196.66 µs | 回退，密集、短分段及仅未知字段均变慢 |
| 6 直接读取单字节键并用完整键分派 | 174.70 → 153.73 µs | 保留 `1ae66e8`，4/5 对达到 10% |

保留版用同一个字段键匹配字段号与编码类型。长键仍使用原变长整数解码器。短分段（8 条）中位耗时下降 5.5%，混有长内容及未知字段的 256 条分段下降 6.1%，仅含未知字段的场景下降 2.4%。四种场景的分配量和次数相同。结果仅测量 Linux Cloud 上的解码环节。

新回归覆盖多字节整数、同一字段重复出现、编码类型不符、未知字段、旧式分组、顺序和截断错误。构建、vet、全量测试和 dmproto、biliapi 的竞态检查通过。Windows amd64 和 Linux 386 测试二进制均已交叉编译，Cloud 内核拒绝执行 386 二进制。逐轮样本、判定和候选补丁位于 Cloud 工作区 `/workspace/bili-danmaku-results/`。
